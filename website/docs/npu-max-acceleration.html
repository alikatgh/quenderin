NPU / Neural Engine — the honest landscape (and why we don't target it yet)

Short version

on-device LLM decode is memory-bandwidth bound, so an NPU mostly helps prefill, not the tokens/sec a user feels in chat. Targeting NPUs means rebuilding — per vendor, with closed SDKs and finicky model conversion — what llama.cpp already gives us portably via Metal (iOS) and Vulkan (Android Adreno).

We use the GPU path now (see GpuOffloadPlanner) and revisit NPUs only if a specific device + vertical justifies the cost. This doc records the analysis so the decision is deliberate, not an omission.

The physics that frames everything

Autoregressive decode generates one token at a time, and each token must stream the entire model's weights through the compute units. On a phone the CPU, GPU, and NPU all hang off the same memory bus, so the bottleneck is memory bandwidth, not raw FLOPs.

A 4-bit 4B model is ~2.5 GB of weights; at ~50 GB/s of usable mobile bandwidth that caps you near ~20 tok/s regardless of which compute unit runs the matmul. (AndroidSoc.kt says this directly: "Decode is memory-bandwidth bound, so GPU/NPU mostly help prefill, not these numbers.")

Where an NPU/GPU does help:

  • Prefill (processing the prompt) — compute-bound and highly parallel, so offload cuts time-to-first-token on long prompts (RAG context, long chats, agent transcripts).
  • Energy — an NPU can do the same work at lower power, which matters for the battery/thermal ceiling (REALITY.md: sustained loops drain ~15–25%/hr and throttle 10–44%).

Neither changes the headline chat tok/s much. That's the trap in "we'll be faster because NPU."

iOS — Apple Neural Engine (ANE) via Core ML

  • The ANE is not generally programmable. You reach it through Core ML, which runs a converted, static graph — not arbitrary transformer ops with a KV cache, dynamic shapes, and custom sampling. Converting an LLM to Core ML that actually lands on the ANE (vs falling back to GPU/CPU) is finicky, per-model work, and Apple controls op support.
  • Apple's own stack splits the difference: Apple Intelligence uses the ANE — but with a model Apple trained and converted in-house on their private runtime. MLX, Apple's open on-device framework, runs LLMs primarily on the GPU (Metal), not the ANE — a strong signal about where the practical win is.
  • What we use instead: llama.cpp's Metal backend (n_gpu_layers = 999 in LlamaEngine.swift). It's a single, uniform, Apple-maintained driver — competitive, zero per-model conversion, and it tracks new models the day they ship in GGUF.

Verdict (iOS): Metal is the right default. An ANE path would be large, per-model, Apple-gated work for a mostly-prefill gain. Not worth it unless a vertical needs the energy win badly enough to fund it.

Android — NNAPI, vendor SDKs (QNN/…), MediaPipe

  • NNAPI is a dead end. Google deprecated NNAPI in Android 15 (2024). Building on it now is building on a sunset API.
  • Vendor NPU SDKs are fragmented and closed. Qualcomm QNN / AI Engine Direct, MediaTek NeuroPilot, Samsung Exynos SDKs — each is a different, per-vendor, often-NDA'd toolchain with its own model-conversion format. Supporting "Android NPUs" means supporting N of these and the matrix of driver versions. That's a team's worth of maintenance for a wrapper project.
  • Google's answer is MediaPipe LLM Inference / AICore (Gemini Nano) — which is the NPU path, but it's Google's stack, gated to specific models and devices. Using it means shipping Google's models through Google's runtime, not running arbitrary GGUF.
  • What we use instead: llama.cpp's Vulkan backend, gated by GpuOffloadPlanner to the GPU family that's actually proven for it — Adreno (Qualcomm/Snapdragon, e.g. the test S23's 8 Gen 2). Mali/Xclipse stay on CPU until a real device proves they're stable and faster (a forceGpu override exists to benchmark them). Portable, open, one codebase.

Verdict (Android): Vulkan-on-Adreno is the pragmatic GPU win today; NPUs are fragmented, closed, and partly sunset (NNAPI). Revisit per-vendor (most likely QNN on Snapdragon) only for a specific device + use case where the prefill/energy gain is the product.

When NPU would be worth it (the honest triggers)

Revisit this decision if any of these become true:

  1. Prefill latency is the product — e.g. long-context RAG or agent transcripts where time-to-first-token, not tok/s, is what the user feels. NPU/GPU prefill offload is real there.
  2. Battery/thermal is the blocker for a vertical — field/industrial use with hours of sustained generation, where the NPU's lower energy-per-token is the difference between shippable and not.
  3. You commit to one platform + one SoC — e.g. a Snapdragon-only enterprise device. Then a single QNN integration is tractable and the fragmentation argument disappears.
  4. A portable NPU abstraction matures — if llama.cpp/ggml grows a maintained NPU backend, we inherit it for free, exactly as we inherit Vulkan today. (This is the most likely path — ride the ecosystem rather than rebuild it.)

Until one of those holds, the GPU path is the correct, honest engineering choice — and it's the one a small open-source team can actually maintain.

What we shipped toward this

  • GpuOffloadPlanner (pure, unit-tested) — safe-by-default, per-SoC Vulkan offload decision.
  • n_gpu_layers plumbed through the JNI (llama_jni.cpp) and Kotlin LlamaEngine.
  • -DQUENDERIN_VULKAN=ON opt-in build flag in android/jni/CMakeLists.txt.
  • Benchmark path — android/verify-llama-link.sh can build CPU and Vulkan .sos for a real device A/B (see docs/DEVICE_VERIFICATION.md). The numbers from a physical Snapdragon device are what turn "Adreno is the proven target" from a documented default into a measured one.

Native acceleration: MAX/Mojo and measured automatic selection

Updated 25 October 2026. This extends Quenderin's native inference work; it does not replace the Remote Harness/Bot delivery. Store submission remains deferred. The current restriction on local weights, native builds and simulator/physical-device runs remains in force.

What the linked posts actually show

  • Chris Lattner's announcement opens the Mojo language and MAX compiler/runtime internals for extension and commercial applications. His thread describes kernel fusion, generated kernels and hardware abstraction. These are execution-backend capabilities.
  • Apurva Mishra's demonstration reports Bonsai 2 2B at 40 tokens/sec on Snapdragon 8 Elite Gen 5 using Modular. The author identifies a GPU path and says NPU synchronization made that attempt slower. Lattner describes the Android work as a custom addition made before their Qualcomm support release. The reported speed is the author's result, not a Quenderin measurement or a guarantee for other devices.

The 26.7 release exposes NVIDIA, AMD, Apple and CPU implementations; it describes other device plugins as upcoming. The package requirements do not supply a native Android/iOS application SDK. That does not invalidate the custom Android demo. The demonstrated port's public source/build recipe has not been located in the author's public repositories or the inspected Modular tree.

Obtain that exact implementation, or produce a reproducible equivalent adapter, before claiming Android MAX support.

Public model inputs do exist: official Bonsai 2 2B GGUF artifacts at revision 683f7be2629342a50987627b40881e54761a2430, with publisher checksums. Quenderin already catalogs bonsai2-2b; adding a duplicate catalog entry would not add the demonstrated execution path.

Match its actual precision, tensor layout, tokenizer, hybrid architecture and activation transforms to the adapter.

Implementation order and acceptance criteria

1. Correct the demonstrated device's classification
  • Recognize Qualcomm's documented SM8850 family and human Gen 5 names before the generic 8 Elite match. Preserve older and unknown device behavior.
  • Classify its GPU family for the existing Vulkan policy; keep CPU selection when Vulkan is absent. Do not advertise NPU support or enable Vulkan globally.
  • Reuse the previous Elite generation's conservative estimate explicitly as an unmeasured fallback. Never import the video's 40 tokens/sec as app data.
  • Test aliases, misleading near-matches, non-Elite names and backend gates.

Delivered scope: AndroidSoc.kt, GpuOffloadPlanner.kt and 13 focused checks in CoreVerify.kt. The complete pure Kotlin verifier passed all 350 checks. No weights, inference, device run or native build was used. Vulkan remains an explicit build option; recognizing a GPU family is not a Gen 5 driver benchmark.

The MAX tensor bridge and Automatic implementation are described below. Mobile MAX inference remains a separate, incomplete milestone.

Grounding: Qualcomm product page lists SM8850 variants. OEM Build.SOC_MODEL formatting remains variable.

2. Turn existing timings into usable local evidence
  • Add an optional performance callback to each concrete engine and its factory. Keep current text-stream interfaces. Capture identity at generation start; avoid a shared last-result getter that another agent run can overwrite.
  • Carry actual model-token counts, prefill/decode durations, first-token latency and maximum gap, completion/error/cancellation status, context/cache conditions, thermal state and the backend actually loaded.
  • Emit only after a successful, uncancelled generation. Partial text is not proof of successful native decoding. Never count rendered text chunks as tokens.
  • Store at most 64 recent records locally, with a bounded encoded size and atomic replacement. Keep prompts, generated text, paths and account IDs out.
  • Key records by verified model artifact identity, runtime revision, actual backend, device/driver signature and comparable context/cache conditions. Ignore incompatible, stale, non-finite and undersized samples.
  • Learn during ordinary inference. No automatic download, warm-up sweep, provider request or background benchmark is needed to collect a sample.

Reports use the already verified artifact receipt, registered runtime and nonunique hardware/OS/execution signature. A source-derived runtime fingerprint invalidates observations when the inference implementation changes. The store holds at most 128 KiB, expires records after 30 days, and contains no transcript, file path or account identity.

Agent, grammar and specialist calls do not train ordinary-chat selection. Android Vulkan observations are ineligible until an exact usable driver identity is available; manual Vulkan behavior is preserved.

3. Add an explicit Automatic policy
  • Introduce its own preference. Do not silently repurpose suggestBestModel, which currently controls task-routing suggestions, or overwrite manual choices.
  • Build candidates from installed, verified, executable model/backend pairs. An advertised model, benchmark record or backend label is insufficient.
  • Apply memory/context, disk, task-modality, runtime and thermal gates first. Within those gates, use comparable observations to evaluate expected response latency; retain current estimates for unknown candidates and label them.
  • Switch only between turns through the existing onboarding/model loader, preserving unload/cancel ownership and recovery to the prior working model. Do not switch a model mid-answer or move a local conversation to a provider.
  • Prefer a stable choice unless measured benefit clears a documented margin; expire failure cooldowns and runtime-specific observations deliberately.
  • Show the selected model/backend and whether its speed is observed or estimated. Remote Harness/API destinations retain their own execution owners.

Automatic defaults off. When enabled, the first admitted ordinary inference of a new conversation can choose an installed text model. That conversation then retains its model; guided computer tasks do not consume its first ordinary turn. Explicit Automatic pins are distinct from older descriptive model metadata. Manual model or speed choices disable Automatic and persist across relaunch.

Three distinct comparable observations are required. Comparison uses exact artifact/runtime/backend/environment/effective context, the same prompt-size bucket, nominal thermal state and the expected cache mode. A retained model's prefix reuse is compared with a freshly loaded alternative's cold observations, never pooled.

Predicted prefill plus decode latency includes switch/load cost; an alternative must improve the prediction by at least 20 percent. Unknown evidence preserves a viable current model. One lazy alternative integrity check and one switch attempt are permitted per new conversation, with one prior-model recovery and a ten-minute failure cooldown. No model sweep is started.

The actual target template/tokenizer, available context and response budget are checked while the existing execution owner exclusively holds the engine. A switch cannot race an ordinary turn, specialist task or agent approval. Drafts, attachments and history must survive preparation and model restoration.

The shared contract and 24 policy fixtures define the cross-platform numeric behavior; platform lifecycle regressions test admission, manual intent, rollback and conversation changes separately.

Its hosted fake-C-API tests compile the actual bridge and exercise cleanup/failure paths under sanitizers. The manual hosted SDK workflow separately inspects exact wheel bytes and their embedded terms before installation can be allowed.

5. Verify before enabling or making speed claims
  • Shared policy fixtures: faster/slower measured candidates, stale runtime, changed artifact/driver, missing backend, insufficient samples and memory veto.
  • A fake 40-token/sec MAX record cannot enable an absent adapter.
  • Cancelled/failed runs cannot train the policy; numeric storage remains bounded and contains no conversation content. Manual mode survives relaunch.
  • Hosted native builds/tests with actual libraries, independent review and exact staged secret scans before source publication.
  • Later authorized hardware validation: same model/artifact, prompt/output lengths, cache state, context, thermal/power conditions and sampling. Compare baseline and MAX latency, throughput, memory and sustained performance.
  • Keep MAX unavailable to Automatic; retain the existing runtime gates and deterministic fallback until a complete model adapter is verified.

Under the current native-run restriction, source/fixture/hosted compilation can advance. Actual phone speed, energy use, driver stability and sustained thermal behavior remain unverified. Store release follows the existing release checklist.

Implementation boundaries

  1. Engine worker: immutable reports, concrete Swift/Kotlin engines and JNI sink.
  2. Policy worker: bounded store, selection policy, shared fixtures and core tests.
  3. Primary integration: Automatic preference, composition, loader/speed controls, integrated validation and fresh independent review.
  4. Backend worker, after a public mobile backend receipt exists: MAX adapter and hosted ABI packaging. The policy must work with existing engines before MAX is admitted.

Use separate file ownership and preserve concurrent edits. Keep all benchmark numbers attributable to the exact source, artifact and hardware that produced them.

The adapter boundary

quenderin_max_model.h defines a narrow contract:

  • Receipt — one to eight app-owned files with exact byte sizes and SHA-256 values, an exact runner ABI, a compiled backend identity and bounded context and output budgets.
  • Runner — supplied by a separately built backend. It owns tokenization, sampling, model semantics and KV-cache behavior. It returns one token piece at a time and must not copy transcripts into diagnostics.
  • Adapter — always hashes the regular app-private files before opening them; requires MAX telemetry and crash-reporting opt-outs; enforces a single-flight lease; reassembles UTF-8 split across token pieces (invalid, overlong, surrogate and truncated sequences become U+FFFD); bounds prompt, output, stream and context bytes; observes cancellation at token boundaries; and emits numeric-only performance data.
  • Capability — reports available only when the static contract, the telemetry opt-outs and a real load probe all pass. Passing load_probe_passed = 1 without a probe is explicitly not done by this module, so Automatic cannot admit MAX from a label or a benchmark record.

The adapter has no vendor dependency. The fake runner and smoke fixture exercise verification failures, symlink rejection, mandatory hashing, telemetry opt-outs, runner open failure, streaming, split and malformed UTF-8, cancellation, sink abort, runner failure, oversized pieces, output and stream caps, context clamping, invalid requests, zero-token tokenization, close-during-generation, single-flight under contention and cleanup.

Residual time-of-check/time-of-use gap: MAX opens the artifact path itself, so a writer with access to the model directory can replace bytes between the adapter's final hash and the vendor open. Receipts therefore require app-private storage; never stage these files in shared or user-writable external storage. The adapter cannot close this gap without a vendor API that accepts an already-open descriptor.

Native bindings

Both bindings wrap the canonical C implementation and link no vendor runner, so opening reports unavailable and MAX stays out of model pickers and Automatic.

  • Android — android/jni/max_jni.cpp compiles the canonical C boundary once, uses registry IDs rather than raw pointers, binds callbacks and cancellation to the active run ID, preserves supplementary Unicode and embedded NUL, and refuses close while busy. The pure-Kotlin facade is MaxModelBinding.kt; a hosted JNI/JVM fixture links the synthetic runner only in the test build. See max-android-binding.md.
  • Apple — apple/QuenderinKit/Sources/CMaxModel is a byte-verified SwiftPM staging of the same C files. The Swift wrapper exposes receipts, capability, streaming generation, cancel and close; close waits for an active run and cancel sets a run-owned stop flag consumed by the C boundary (idle cancel is a no-op). Tests use a test-only Swift runner. See max-apple-binding.md.

Neither binding is compiled with a production runner, and no weights or vendor SDK were downloaded. Hosted JNI/JVM and Swift tests are compilation/fixture evidence, not MAX execution or phone performance.

The cancellation correction at 110b67e (docs commit a56a382) now has narrow hosted verification on codex/max-cancel-verification-20261026: native-remote-sdk.yml run 40221763739 completed both the apple job (QuenderinKit swift test, Apple/iOS SDK/app compile) and the android job (core tests, SDK/app build) successfully.

This is a two-job run, not the full CI matrix, and it does not execute the local host JNI/JVM synthetic fixture. The earlier full-CI green set at 065b740 remains separate evidence. No vendor backend, physical phone, rendered UI or store verification is established.

Why mobile MAX is still blocked

  1. No public mobile backend. Both the pinned source revision 527d069ee11a41ac5320af1f9402db0a66b2b868 (26.7.0, 13,588 paths) and main 8d5597… (16,637 paths) contain no Android, Adreno, Qualcomm, Hexagon, QNN or Dragonfly path. The official blog defers those plugins. The demo's custom port is not public, and no Android or iOS wheel is published.
  2. No Bonsai MEF contract. The official prism-ml/Ternary-Bonsai-2-2B-gguf file is pinned (683f7be2629342a50987627b40881e54761a2430, 429,183,456 bytes, SHA-256 36061ad4…), but a MEF conversion, weight mapping, tokenizer contract, sampling/stops and multi-turn cache behavior are all missing. Matching the PTQ1_0/Hadamard layout is not optional.
  3. Licensing and telemetry are unresolved for mobile. Published 26.7.0 wheels declare LicenseRef-MAX-Platform-Software-License; the inspected SDK embeds the August 18, 2026 Community License with the same SHA-256 recorded for the pinned source license. That metadata label does not establish different terms. Mobile redistribution still needs review of the exact components, third-party notices and distribution requirements. MAX usage data is described as collected by default, so opt-outs must be proven in the actual mobile artifact.
  4. No iOS artifact. MAX supports Apple Silicon through Metal on macOS. That does not create an iOS framework, signing identity or app-store-safe binary. The pinned C API compiles a MEF at runtime, so an ahead-of-time path and the platform's executable-memory rules must be resolved before this can be an app target.
  5. No phone evidence. Inference speed, memory, driver stability, sustained thermals, battery and rendered UI require the device runs the project has explicitly deferred.

SwiftPM cannot reference files outside the package root, so the canonical C headers and implementation are staged byte-for-byte into the C target. The staging receipt records the canonical path, size and SHA-256 of each file; --check fails if the staged bytes drift. CI runs the check before swift test and before the cross-target SDK build. There is no second maintained copy.

The Swift wrapper exposes receipt verification, capability, open, streaming generation, cancel and close. close() waits for an active generation to drain and returns .busy when called from the token callback itself. cancel() sets a run-owned stop flag consumed by the C boundary, so a synchronous generation cannot block cancellation; idle cancellation is a no-op.

Tokens own pending and terminal cancellation state; a delayed, completed or foreign token cannot cancel a later run. Errors and numeric reports are Swift value types; no transcript, path or prompt is put in an error.

Tests

  • receipt verification and tamper rejection, rejected unsafe receipts;
  • unavailable open with no runner;
  • streaming hello é! across a split UTF-8 character;
  • cancellation from the token callback and after admission but before the first token;
  • BUSY while another run holds the lease;
  • close() waits for the run to drain and returns .closed;
  • idle cancel during a blocked close does not touch the model;
  • token-owned cancellation is isolated from a successor run, including delayed token and delayed current-run requests;
  • completed, foreign and already-consumed tokens are rejected;
  • reuse after cancellation, idempotent close, closed-handle rejection;
  • close from the callback is refused, not deadlocked.

The bridge compiles the canonical C implementation once; it does not copy or fork it. Handles are registry IDs, not raw pointers. Each call holds a shared_ptr, so a concurrent close cannot free state under a caller. The Java lease and the C lease must both admit before generation touches the model.

Callbacks are resolved to MaxTokenSink.onToken(String): Boolean; the callback runs on the generation thread. Cancellation is run-owned: each run has its own pending, active or completed state. A token cancelled before native admission keeps an independent pending request; a completed or retired token is rejected, and a delayed earlier token cannot cancel the active run.

Pending requests are bounded to 64 and terminal history to 1,024 completed IDs. Only terminal records expire: unknown IDs at or below the retirement floor cannot be revived, while an accepted pending request remains live even if that floor passes it. nativeClose refuses with QMAX_BUSY while a run is active.

Prompt conversion preserves supplementary Unicode and embedded NUL; paths use the strict converter and reject NUL. The bridge never treats JNI modified UTF-8 as ordinary UTF-8.

MAX native tensor bridge

This module implements qmax_open, qmax_execute and qmax_close over MAX's real C API. It owns runtime/model/tensor lifetimes, checks bounded float32 shapes, commits output only after validation and checks stop requests between synchronous execution steps. The fixture exports a four-element CPU graph and expects [2, 6, 12, 20] from the native executor.

The bridge is groundwork for a model adapter. It does not tokenize prompts, load GGUF, generate language tokens or register MAX as a selectable mobile LLM. A Bonsai adapter still requires a verified MEF/weight/tokenizer/cache contract, and Android requires an actual NDK/Adreno port.

MAX's public synchronous C API cannot interrupt an execution already in flight; a supervising process deadline is required. No pretrained model is used by this module's tests.

Mobile model-adapter boundary

include/quenderin_max_model.h and src/quenderin_max_model.c add the vendor-neutral lifecycle a mobile backend must satisfy: receipt files that are always hashed (exact sizes and SHA-256), an exact runner ABI, telemetry/crash-reporting opt-outs, single-flight generation, bounded prompt/output/context/stream budgets, strict UTF-8 reassembly across token pieces, cancellation at token boundaries, capability probing and numeric performance reports.

qmax_model_close refuses with QMAX_BUSY while a generation is active. It owns no tokenizer, sampler, weights or GGUF loader; those stay in the vendor runner.
