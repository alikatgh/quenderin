Quenderin for Android

Native Android client. Same architecture as iOS: a portable, tested brain in pure Kotlin, a thin JNI adapter to llama.cpp, and a Compose UI — built so everything that can be proven without a device is proven, and the rest is a clearly-marked cliff.

Layout

text
android/
├── quenderin-core/      Pure-Kotlin/JVM brain — NO Android deps. The source of truth.
│   ├── ModelCatalog · ModelRecommender · MemoryFitness · SafetyBlocklist
│   ├── AndroidSoc · AndroidDeviceProfile · AndroidModelSelector · ThermalBattery
│   │      ↳ device-aware picker (native-heap budget + chip + disk + heat/battery),
│   │        twin of iOS IPhoneModelSelector — unlocks 7B on 12–16 GB flagships
│   ├── InferenceEngine (seam) · MockInferenceEngine · LlamaEngine (JNI adapter)
│   ├── ModelDownloader (seam) · MockModelDownloader
│   ├── DownloadPolicy · DiskSpace · OfflineReadiness · DownloadStore  (M3 offline + resume)
│   ├── AgentTool · AgentDecision · AgentLoop · ScriptedInferenceEngine  (M4 agent loop)
│   ├── OnboardingModel (M1 state machine) · ChatModel (M2)
│   ├── src/verify/CoreVerify.kt   ← headless harness (kotlinc + java, 139 checks)
│   └── src/test/…/CoreTest.kt     ← JUnit mirror (./gradlew test)
├── jni/                 C++ bridge to llama.cpp (llama_jni.cpp + CMakeLists.txt)
└── app/                 Jetpack Compose app over the core (MainActivity + ui/)

Verify the brain headlessly (no Gradle/Android needed)

sh
KOTLINC="/Applications/Android Studio.app/Contents/plugins/Kotlin/kotlinc/bin/kotlinc"
cd android/quenderin-core
bash "$KOTLINC" src/main/kotlin/ai/quenderin/core/*.kt src/verify/CoreVerify.kt \
    -include-runtime -d /tmp/qcore.jar && java -jar /tmp/qcore.jar    # → ALL PASSED

This is the Android equivalent of swift test for apple/QuenderinKit. It proves the catalog + recommendation match the other platforms, memory fitness, the safety blocklist, the LlamaEngine off-device fallback, and the M1/M2 onboarding + chat flows.

Run the app (mock engine)

Open android/ in Android Studio → run app. The full onboarding → chat flow works on MockInferenceEngine; no llama.cpp required.

What the selector picks (and why Android differs from iOS)

AndroidModelSelector gates each model on memory + chip speed + disk, then defaults to the largest comfortable model. Android's memory reality differs from iOS, and the picks show it:

DevicePickWhy
4 GB mid-rangeLlama 3.2 1Bbudget ~2.2 GB; 3B too big
6 GB Snapdragon 8 Gen 2Qwen3 4Bthe mainstream sweet spot
8 GB Snapdragon 8 Gen 3Qwen3 4Bcomfortable; 7B offered (tight)
12 GB + slower chipQwen3 4BRAM allows more, but the chip is the limit
16 GB Snapdragon 8 EliteMistral 7BRAM + a fast chip unlock a 7B no 8 GB iPhone can hold

Two Android-specific truths, both from the measured research (apple/REALITY.md):

  • Native heap, not jetsam. llama.cpp allocates via JNI on the native heap, which is bounded by total RAM + the low-memory-killer — not the tiny Dalvik per-app cap. So budgets are more generous than iOS, and the 12–16 GB tiers (common on Android) unlock bigger models.
  • The 7 tok/s floor keeps 14B off phones — it's too slow to feel alive even at 16 GB.

ThermalBattery attaches the same heat/battery advisory as iOS.

Go real

Linking llama.cpp (NDK + CMake) and running on a device is the on-device cliff — see INTEGRATION.md. MainActivity auto-switches to the real engine once the native .so is built; no code change required.

Parity rule

ModelCatalog + ModelRecommender must stay identical across desktop (src/constants.ts), iOS (apple/QuenderinKit), and here — enforced by scripts/check_catalog_parity.py (npm run check:catalog-parity). The selectors (AndroidModelSelector / IPhoneModelSelector) are platform-specific by design; the catalog is the shared part.

Android integration — native 0.5.0 model update

This is the Android twin of apple/QuenderinKit/INTEGRATION.md. The native 0.5.0 candidate uses the locked Prism runtime, verified Muse source patch and isolated image runtime. A stock llama.cpp checkout does not provide these capabilities.

The update expands the shared text catalog to 28 entries, including complete-part Beam and Muse installation. Dedicated workflows cover still-image questions with managed vision model/projector pairs, explicit Hy-Memory proposals, receipt-verified Granite Switch imports, Step 5 Preview through a user-owned CUDA host, and isolated FLUX/MOSS image generation.

Resource leases, memory floors and cancellation guard these workflows; availability depends on each model's artifacts and device capacity. See docs/bonsai-2.md for exact sources and limits. Source integration and hosted compilation do not establish full-weight inference or image quality.

The source declares versionCode = 5, versionName = "0.5.0", and compile/target API 36. Build with AGP 8.10.1, Kotlin/Compose compiler 2.2.21, and the checked-in Gradle 8.11.1 wrapper. The SDK packages used by the build are platforms;android-36, build-tools;35.0.0, ndk;26.3.11579264, and cmake;3.22.1; Java source/bytecode targets remain 17.

The wrapper verifies its distribution against Gradle's published SHA-256. Code 5 is provisional until the highest uploaded Play version code is refreshed.

The historical 2026-06-14 smoke test used NDK r26d and an arm64 emulator with an older runtime, reporting coherent output and about 102 tok/s. It does not verify 0.4.0, 0.5.0, Bonsai, Muse, Android 16, or physical-phone performance. The legacy verify-llama-link.sh path is a device smoke-test helper, not the current source preparation or release-build procedure.

The app boots on MockInferenceEngine when jni/llama.cpp is absent so onboarding → chat runs in Android Studio without NDK. MainActivity switches to real LlamaEngine automatically once libquenderin_llama.so is present (Gradle auto-enables externalNativeBuild when the checkout exists).

Demo mode is labeled in chat + Settings and mock replies say they are canned. Release/bundle builds fail without jni/llama.cpp unless you pass -Pquenderin.allowMockRelease=true (intentional demo APK only).

Debug builds without a native checkout

Open android/ in an Android Studio version compatible with AGP 8.10.1, or run ./gradlew :app:assembleDebug. Without a native checkout this compiles the demo engine; it cannot establish native inference support. The Gradle wrapper is already checked in. Building does not require an emulator or model weights.

Prepare and compile the pinned native runtime

llama.cpp stays C/C++; jni/llama_jni.cpp is the only glue (twin of the Swift adapter).

  1. From the repository root, prepare the runtime at a new or matching destination:
sh
   quenderin_root="$PWD"
   python3 scripts/prepare_prism_runtime.py fetch --destination "$quenderin_root/android/jni/llama.cpp"
   python3 scripts/prepare_prism_runtime.py verify --source "$quenderin_root/android/jni/llama.cpp"

This downloads source only. The lock is shared/prism-runtime.json; the helper verifies the base revision, applies the locked Muse patch, and verifies its files. It refuses to replace a mismatched existing checkout. Choose a separate destination if android/jni/llama.cpp already contains other work and pass that absolute path below. The example checkout is gitignored.

  1. Build the isolated image runtime in a new absolute work directory, using the established NDK. Replace the example SDK/work paths with your own:
sh
   quenderin_diffusion_work="/absolute/new/android-diffusion"
   ANDROID_NDK_HOME="/absolute/path/to/Android/sdk/ndk/26.3.11579264" \
     bash scripts/build_android_diffusion.sh "$quenderin_diffusion_work"

The builder refuses an existing work path. It fetches pinned source, statically links its private C++ runtime, strips and seals both image DSOs, and verifies their identity, dependencies and 16 KiB alignment. It downloads no model weights.

  1. Build the app and run the JVM unit tests with both explicit runtime paths:
sh
   cd "$quenderin_root/android"
   ./gradlew :app:assembleDebug :app:bundleRelease :quenderin-core:test \
     --no-daemon --console=plain \
     -Pquenderin.runtime=prism \
     -Pquenderin.llamaDir="$quenderin_root/android/jni/llama.cpp" \
     -Pquenderin.diffusionLibDir="$quenderin_diffusion_work/jniLibs"

Gradle enables CMake/NDK automatically and builds arm64-v8a JNI plus the CPU backend variants. CMake rejects missing or altered Prism/Muse provenance. No model weights are downloaded by these build tasks.

  1. Verify the actual packaged libraries in both outputs:
sh
   cd "$quenderin_root"
   python3 scripts/verify_diffusion_android_package.py \
     --libraries "$quenderin_diffusion_work/jniLibs" \
     --package android/app/build/outputs/apk/debug/app-debug.apk
   python3 scripts/verify_diffusion_android_package.py \
     --libraries "$quenderin_diffusion_work/jniLibs" \
     --package android/app/build/outputs/bundle/release/app-release.aab

This verifies sealed image-library bytes, dependency closure and 16 KiB ELF alignment after AGP packaging. Gradle also rejects a Prism release without the verified image-runtime directory.

  1. The bundle is android/app/build/outputs/bundle/release/app-release.aab. Without android/keystore.properties it is unsigned. Reuse the registered upload key for a signed Google Play update; do not create a replacement key as a workaround. See docs/RELEASE.md for the signing and console steps.

CI uses the same explicit runtime selections and compiles an unsigned release bundle. A passing job proves compilation and package verification of that revision, not signing, upload, submission, installation, or inference with the real model weights.

Keep the C API in sync

llama_jni.cpp targets the post-2024 llama.cpp API (llama_model_load_from_file, llama_init_from_model, the llama_vocab + llama_sampler chain). The API moves — if the build breaks, diff against jni/llama.cpp/include/llama.h at your pinned commit and adjust (same discipline as the iOS adapter, which was checked against llama.h).

CPU-variant backends (0.2.1 default)

jni/CMakeLists.txt builds ggml's Android CPU variant set (android_armv8.0 … armv9.2, DOTPROD/I8MM) as dlopen-able plugins. The JNI loads them from applicationInfo.nativeLibraryDir and ggml picks the best match for the live CPU. Packaging: useLegacyPackaging = true is required — AGP otherwise leaves the .so files inside the APK and the scan finds zero devices.

Affinity (ggml_threadpool_new) is resolved at runtime from the CPU backend registry, not linked into libquenderin_llama.so (link-time was an undefined-symbol with GGML_BACKEND_DL).

Optional — GPU offload (Vulkan)

CPU-variant backends are the default win. Vulkan stays opt-in because the vendored llama.cpp Vulkan backend requires SPIRV-Headers at configure time (not in the NDK). To build it:

kotlin
// android/app/build.gradle.kts → externalNativeBuild { cmake { ... } }
arguments += "-DQUENDERIN_VULKAN=ON"
buildConfigField("boolean", "QUENDERIN_VULKAN", "true")   // tell Kotlin the .so has the backend

Then let GpuOffloadPlanner decide per SoC whether to actually offload, and pass the result to the engine — so a Vulkan build stays safe on every device (Adreno offloads; Mali/Xclipse stay on CPU):

kotlin
val soc = AndroidSoc.fromSocModel(Build.SOC_MODEL)           // API 31+
val gpuLayers = GpuOffloadPlanner.recommend(soc, vulkanAvailable = BuildConfig.QUENDERIN_VULKAN)
val engine = LlamaEngine(deviceBudgetGb = budget, gpuLayers = gpuLayers)
Why a decision and not just "all layers"

Android Vulkan driver quality is heterogeneous, and on mobile decode is memory-bandwidth bound — GPU offload mainly speeds prefill (long-prompt time-to-first-token), not steady tok/s. Background + measured rationale: docs/NPU_NEURAL_ENGINE.md. A/B it on your device with QUENDERIN_VULKAN=1 ./verify-llama-link.sh (see docs/DEVICE_VERIFICATION.md).

Downloads and Android 16 validation

The native app uses a WorkManager dataSync foreground worker with disk/memory preflights, resumable transfers, artifact verification, and persisted progress. Muse is a multipart installation; all required shards must verify before loading. The demo-only MockModelDownloader does not download weights.

The API 36 source audit found existing Compose Scaffold/system-bar/IME inset handling and no edge-to-edge opt-out or legacy onBackPressed interception. Android 16 job quotas also apply to long-running foreground WorkManager jobs; large background downloads can pause when quota is exhausted.

Physical-device checks must still establish download stop/resume behavior, keyboard and system bar layout, predictive back, and lifecycle recovery. These checks were not run for the build-only 0.4.0 preparation.

Measure on a physical phone before promotion

On a physical device, capture tok/s, time-to-first-token, peak RAM, and battery for the recommended model. That's the number that tells us whether the "50-year-old, off-grid, asks a question" story actually holds — and it can only be measured here.

Quenderin — Android (Kotlin)

The Android port, started the same way as iOS: the portable Kotlin "brain" first, compiled and tested, before the device-coupled parts.

quenderin-core is a pure-Kotlin/JVM module (no Android framework deps), so it compiles and unit-tests without a device — and it mirrors the Swift apple/QuenderinKit and the desktop src/constants.ts exactly. All three platforms must agree on the catalog and the recommendation.

What's here

FileRole
ModelCatalog.ktThe 11-model catalog (Qwen, DeepSeek, Gemma, Phi, Mistral, Llama) + quantization table
ModelRecommender.ktdevice RAM → recommended model — Qwen3-first, identical thresholds to Swift/TS
MemoryFitness.kt"Can this device load it?" — same 0.85/0.65 budgets
SafetyBlocklist.ktThe agent's hard sandbox (Pay/Delete/Password…)
InferenceEngine.ktThe runtime-agnostic seam + MockInferenceEngine

Verify

Headless, with just the Kotlin compiler (Android Studio bundles one) — no Gradle needed:

bash
KOTLINC="/Applications/Android Studio.app/Contents/plugins/Kotlin/kotlinc/bin/kotlinc"
cd android/quenderin-core
bash "$KOTLINC" src/main/kotlin/ai/quenderin/core/*.kt src/verify/CoreVerify.kt -include-runtime -d core.jar
java -jar core.jar      # → 139 checks, ALL PASSED

Or, in Android Studio / with Gradle: ./gradlew test (runs src/test JUnit).

The architecture (same engine, thin Kotlin adapter)

Quenderin runs llama.cpp on every platform; only the adapter differs. On Android that adapter is Kotlin + JNI over the NDK (already installed at ~/Library/Android/sdk/ndk):

text
Quenderin (Android app)
  └─ :app            Jetpack Compose UI + WorkManager downloads
      └─ :quenderin-core   this module (probe, catalog, recommend, fitness, safety, seam)
          └─ LlamaEngine (Kotlin) ── JNI ──► llama.cpp (C/C++)  ← built with the NDK

Next steps (mirror iOS)

  • LlamaEngine.kt + a JNI .cpp bridge → llama.cpp built via the NDK (the real inference; needs a device/emulator + a GGUF to verify — the same cliff as iOS).
  • HardwareProbe real impl via ActivityManager.MemoryInfo (the core keeps it abstract so the JVM build stays pure).
  • Background/resumable downloader via WorkManager + DownloadManager.
  • The :app Compose module: onboarding → chat, on the mock engine first.

See ../../apple/ARCHITECTURE.md for the cross-platform picture.

Building & running the native apps (iOS + Android)

How to take the Swift (apple/) and Kotlin (android/) apps from source to a running install. Two tiers per platform:

  • Bring-up (mock engine) — the whole UI flow (onboarding → chat → agent) runs with no model file. Fastest way to see the app on a device/simulator.
  • Real on-device inference — link llama.cpp so the app actually generates tokens.

What's verified end-to-end in this repo (2026-06-14, no CI):

  • iOS app builds + runs on the iPhone 17 simulator (Xcode 26.3): xcodegen → xcodebuild -sdk iphonesimulator → install + launch; the model picker renders a device-aware recommendation (Apple M4 → Llama 3.2 3B Balanced).
  • Android app builds + runs on a booted arm64 emulator: ./gradlew :app:assembleDebug → adb install → launch; picker renders (low-mem emulator → Llama 3.2 1B).
  • Real llama.cpp inference runs on both: iOS apple/verify-llama-link.sh (~135 tok/s, CPU, Mac) and Android android/verify-llama-link.sh on the emulator (~102 tok/s, CPU, arm64). The real-inference Android APK loads libquenderin_llama.so (NATIVE_AVAILABLE true). QuenderinKit compiles in all engine modes (swift build); Android core 99/99.

What still needs a physical device (ground-truth numbers only — the path is proven):

  • A real iPhone for Metal tok/s + battery + thermals, and a real Android phone for SoC tok/s. The Mac/sim/emulator numbers are host-CPU ceilings.

iOS

Prereqs
  • Full Xcode (not just CommandLineTools): xcode-select -p must point at …/Xcode.app/Contents/Developer. Switch with sudo xcode-select -s /Applications/Xcode.app.
  • brew install xcodegen
A. Bring-up (mock engine) — clickable app, no model ✅ verified
bash
cd apple/QuenderinApp
xcodegen generate            # → Quenderin.xcodeproj (+ Info.plist, both git-ignored)
open Quenderin.xcodeproj     # then Run (⌘R) on an iPhone simulator
# …or fully headless (what was verified here):
xcodebuild -project Quenderin.xcodeproj -scheme Quenderin -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 17' build
xcrun simctl install booted "$(find ~/Library/Developer/Xcode/DerivedData -name Quenderin.app -path '*iphonesimulator*' | head -1)"
xcrun simctl launch booted ai.quenderin.Quenderin

The app runs the full flow on MockInferenceEngine. The engine is chosen by DefaultInferenceEngine.make() — mock until llama.cpp is linked (next).

B. Real on-device inference — Route A, the shippable path
bash
# 1. Build the llama.cpp xcframework (device + simulator + macOS slices; needs Xcode)
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
./build-xcframework.sh        # → build-apple/llama.xcframework

# 2. Drop it into the package — Package.swift auto-detects it (no edits needed)
mkdir -p ../apple/QuenderinKit/Frameworks
cp -R build-apple/llama.xcframework ../apple/QuenderinKit/Frameworks/

# 3. Regenerate + run — canImport(llama) is now true, Metal GPU included
cd ../apple/QuenderinApp && xcodegen generate && open Quenderin.xcodeproj

Frameworks/*.xcframework is git-ignored (large binary — ship via Git LFS or a CI step).

Faster local check without the xcframework (macOS only, Route C): point the package at a dev build of llama.cpp — see apple/QuenderinKit/INTEGRATION.md and apple/verify-llama-link.sh.

Bigger models (optional)

To hold 4B+ comfortably before iOS jetsam kills the app, add the com.apple.developer.kernel.increased-memory-limit entitlement (needs a provisioning profile that allows it). Not required for bring-up or for 1–3B models.

Android

Prereqs
  • Android Studio (or the command-line SDK) with platform 35 + build-tools 35.
  • For real inference only: the NDK (sdkmanager "ndk;26.3.11579264") + CMake.
  • A committed Gradle wrapper (./gradlew, pinned to 8.9 to match AGP 8.5.2) — no separate Gradle install needed. JDK 17 for the build (JAVA_HOME=…/openjdk@17).
  • android/local.properties with sdk.dir=<your Android SDK> (git-ignored).
A. Bring-up (mock engine) — clickable app, no model, no NDK ✅ verified

The app boots on MockInferenceEngine the moment it opens. This build is verified in-repo — produces app-debug.apk (ai.quenderin.app, label "Quenderin", target SDK 35):

bash
cd android
echo "sdk.dir=$ANDROID_SDK_ROOT" > local.properties     # one-time
JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew :app:assembleDebug
#   → app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/debug/app-debug.apk  # to a device/emulator
# (Or just open the android/ folder in Android Studio and hit Run.)

MainActivity already uses the real WorkManagerModelDownloader, and selects the engine with if (LlamaEngine.NATIVE_AVAILABLE) LlamaEngine() else MockInferenceEngine() — so it stays on the mock until the native .so is present (next).

B. Real on-device inference — build the JNI bridge against llama.cpp
bash
# 1. Add llama.cpp where the JNI CMake expects it (or pass -DLLAMA_DIR=…)
git submodule add https://github.com/ggml-org/llama.cpp android/jni/llama.cpp

# 2. In android/app/build.gradle.kts, uncomment:
#      ndk { abiFilters += listOf("arm64-v8a") }   // + "x86_64" for the emulator
#      externalNativeBuild { cmake { path = file("../jni/CMakeLists.txt"); version = "3.22.1" } }

# 3. Build — produces libquenderin_llama.so, flipping LlamaEngine.NATIVE_AVAILABLE true
JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk

See android/INTEGRATION.md for the JNI details. The native build is CPU (GGML_OPENMP off); GPU/NNAPI deltas mainly affect prefill (decode is memory-bandwidth bound — see apple/REALITY.md).

Why useLegacyPackaging = true stays set (r8 R3): AGP's default keeps .so files compressed in the APK and dlopens them via mmap-from-APK — but ggml's backend enumeration scans a real directory for its backends, which the mmap path doesn't provide, so backend discovery silently fails (BUG_JOURNAL, 2026-06).

Legacy packaging extracts the libs to disk where the scan works. Re-audit this whenever AGP is upgraded — if a future ggml loads backends without the directory scan, the ~30–60 MB install-size cost can be reclaimed.

After it runs on a real phone

Replace the interpolated chip-score estimates with ground truth: capture decode tok/s, post-throttle steady-state, and battery drain on physical A15/A17/A18 + a Snapdragon flagship, then update the calibration tables (apple/REALITY.md documents the method).

Sign the verified Android candidate locally

The hosted candidate remains unsigned and draft-only. The signer accepts only the currently pinned Google Play upload certificate. It signs an existing hosted AAB; it does not build Android/native code, change the Play upload key, upload anything, or read android/keystore.properties.

The separate replacement-key generator below is for the user's explicitly authorized upload-key reset preparation.

The expected upload certificate SHA-256 is 8B:38:F4:E5:85:88:3A:B7:37:F2:91:8F:49:90:BA:40:17:67:A0:39:37:EB:2A:68:72:88:BD:E3:E9:49:CF:3D. The existing private keystore location and alias remain unverified. On 2026-10-28, the user explicitly authorized a bounded search and a replacement upload key if the original could not be found.

The bounded follow-up located no usable key; repository and github-pages environment Actions secret counts were both zero. This does not establish permanent loss of the original key.

The cached official npm Varlock launcher at ~/.local/varlock/1.23.0/varlock and JDK 21 signing tools were checked on this Mac on 2026-10-28. No additional download or installation is required. The wrapper pins version 1.23.0, uses only the adjacent explicit public signing.schema, disables telemetry and cache, and emits only validation booleans/status.

Password variables and the private path/alias are marked sensitive. No credential value is written to a file. Pinned Varlock was tested with this custom filename passed through --path: synthetic inputs validate, while omission of each required input is rejected. No dotfile is needed or published.

Prepare the authorized replacement upload key

This is an offline private Terminal step; the agent does not receive the password or invoke real key generation. It creates a replacement upload key. Google's existing app signing key, application ID and installed-user update identity remain unchanged. Nothing is requested or submitted to Google by this helper.

Check the exact installed tools without credentials or a keystore:

sh
python3 -B tools/android-release/generate_upload_key.py check

All three booleans must be true: varlock1230, jdk21, keytoolAvailable. In your own Mac Terminal, from this checkout, run:

sh
zsh tools/android-release/generate-with-prompts.zsh

Enter a new absolute directory outside every Git checkout, with an existing parent and no symlink components. One suitable location is a new directory under your existing ~/Library/Application Support/ folder; expand ~ to the absolute path at the hidden prompt.

Enter and confirm one new password of at least 12 characters. Both entries are hidden, passed through pinned Varlock, and cleared from the wrapper's environment on exit. Keep this password in your existing password manager through its private interface; never send it in chat or put it in command arguments, a plaintext file, .env, logs or repository files.

The helper creates exactly these files in the new directory:

  • upload-keystore.p12: private RSA 3072-bit PKCS12 upload key; alias quenderin-upload, SHA256withRSA certificate, validity 10,000 days. Its subject CN=Quenderin upload key labels the project and asserts no owner's legal identity.
  • upload_certificate.pem: public certificate only, for Google's reset form.
  • upload-key-reset.receipt.json: public fingerprint and preparation status; resetRequested and registeredForPlay are both false.

The directory is mode 0700 and files are mode 0600 under umask 077. macOS extended ACLs are checked through descriptor metadata; any ACL-bearing output is rejected, including inherited grants hidden by those mode bits. If the new empty directory inherits an ACL, generation stops before creating a key.

Existing ancestors and their permissions are never changed. Directory descriptors anchor creation and checks, and fixed relative keytool filenames resolve in that directory; ancestor identity, Git markers and output privacy are rechecked between phases.

The generator never reads private keystore bytes. Only JDK keytool creates/accesses the key; passwords reach it by environment-variable name. Tool output is captured and only fixed status is printed. Each command has an owned process group. Timeout or interruption stops that group with TERM, escalates to KILL when needed and reaps its direct child.

The outer Varlock supervisor gives the inner generator time to stop its own keytool group before escalating. Signal handlers are installed before spawning; cancellation during startup is deferred until the child PID is owned, then its group is stopped before rejection returns.

Existing paths, files and symlinks are rejected before generation. A failed operation preserves every newly created file. A generated .p12 remains a private signing identity even if PEM export, fingerprint checks or receipt writing later fails: never delete it as scratch or regenerate over it.

Keep the directory private and recover the public certificate from that same key after diagnosing the failure. A partial receipt is not success evidence; do not submit it. There is no automatic deletion, overwrite, regeneration or retry.

Preflight rejection reports status: "rejected" and privateOutputMayExist: false. Once generation can have started, failure reports status: "preserved_output_requires_recovery" and privateOutputMayExist: true. The outer supervisor reports this conservatively after dispatching Varlock, including a timeout that prevents the child from reporting its exact phase.

It does not prove that key creation completed. Inspect the chosen directory privately before taking another action. Preserve any .p12 there and its password; recover its public certificate from the same key rather than rerunning generation. Send only the public certificate location or fingerprint when recovery is complete.

After successful private entry, share only the public certificate location or its public SHA-256 fingerprint. Do not upload or send the .p12 file or password.

Register the replacement with Google

Use the existing Quenderin ai.quenderin.app Play Console record and the correct signed-in profile. Open Protected with Play → Play Store protection → Manage Play app signing, then Upload key certificate → Request upload key reset. Select the truthful reason that the existing upload key could not be located, upload only upload_certificate.pem, and submit the already-authorized reset. Do not choose an app signing key upgrade or create another app record.

Record the reset receipt and the effective date/time Google displays or confirms. The current official help does not specify a guaranteed completion interval; do not promise a fixed 48-hour wait. Verify the effective upload certificate fingerprint in Play against the new receipt before enabling it in the signer.

Only after that verification, update the public CERT_SHA256 pin and its focused tests to the confirmed certificate. The current pin stays unchanged during key generation and reset preparation, so the signer intentionally rejects the new key until that separate change is verified.

Then use the signing command below with the new .p12 location, alias quenderin-upload, and the same password twice.

Official references: Google's upload-key reset procedure, upload key versus app signing key.

Sign the exact hosted candidate

Check availability without accessing a keystore:

sh
python3 -B tools/android-release/sign_aab.py check

After the exact reviewed source has passed the hosted workflow, download its three draft assets and verify the GitHub asset digest and .sha256 against that exact draft/source. In your own Mac Terminal, use the existing key's private path, alias and passwords at these hidden prompts:

sh
zsh tools/android-release/sign-with-prompts.zsh \
  --bundle /absolute/path/quenderin-android-0.6.0-6-SHORTSHA-unsigned.aab \
  --receipt /absolute/path/quenderin-android-0.6.0-6-SHORTSHA-unsigned.aab.receipt.json \
  --receipt-sha256 VERIFIED_GITHUB_RECEIPT_ASSET_SHA256_WITHOUT_PREFIX \
  --output-dir /absolute/path/new-signed-candidate-directory \
  --source-commit FULL_REVIEWED_40_CHARACTER_SHA \
  --version-name 0.6.0 --version-code 6

Replace the placeholders with the exact verified artifact and reviewed commit. Obtain the expected receipt SHA-256 from that draft's GitHub asset metadata, independently of the downloaded local receipt. The hidden prompts export inputs only to this command; the shell clears them on exit.

Alternatively, a human who already exported the four QUENDERIN_UPLOAD_* variables may invoke sign_aab.py sign with the same arguments. Never enter actual values in chat, command arguments, .env files, logs or repository files.

Varlock validates/injects the inputs, then keytool checks the existing upload certificate before signing. jarsigner receives passwords by environment-variable name, without password arguments. The wrapper checks the exact source/version, unsigned AAB digest and Prism/image/Noise/JNA provenance; verifies the final JAR signature and the actual packaged certificate; and compares every original payload entry byte-for-byte after signing.

Signature metadata is the only allowed addition. Android upload certificates are self-signed, so the fixed certificate pin and JAR signature verification are used instead of requiring a public CA trust chain.

The output directory must be new. Successful signing writes exactly the signed AAB, its SHA-256 and a signing receipt. A rejected operation may leave an incomplete new output directory; it produces no success receipt and must not be uploaded. The original candidate and keystore are preserved. No timestamping, network access, automatic retries, output overwrite or Play upload is performed.

References: Varlock CLI and --path, JDK jarsigner, JDK keytool.
