Backend

The TypeScript backend in src/. It runs as a plain Node server (npm run dashboard) or wrapped in Electron (npm run electron:dev).

Entry points

FileRole
src/index.tsCLI (commander): dashboard (server + UI) and agent (headless agent loop)
src/server.tsBoots Express + WebSocket, dependency-injects services, temp-file cleanup, graceful shutdown, process-level safety nets
src/app.tsThe Express app: all /api/* routes, static UI from public/
src/electron/main.tsElectron main process — owns the dashboard server + the window
src/electron/preload.tscontextBridge API (no nodeIntegration)
src/constants.tsModel catalog, RAM tiers, limits/thresholds

Services (src/services/)

LLM (llm.service.ts)

The core. Loads/unloads GGUF models via node-llama-cpp, runs inference with AbortController-based timeouts (real cancellation), tracks the GPU backend and flash-attention state, and manages the model catalog (MODEL_CATALOG), downloads (resumable, with progress events), and memory-fitness checks (checkMemoryForModel) so it refuses to load a model that won't fit. Lifecycle: idle models are released after a timeout to reclaim RAM.

Agent (agent.service.ts + agent/)

The OS agent loop — runAgentLoop(goal, emitter, attachments, maxSteps, maxWallClockMs). Composed of:

  • agent/promptBuilder.ts — assembles perception + history into the planner prompt.
  • agent/actionExecutor.ts — maps the LLM's symbolic action ({action,id}) to real input, with the safety blocklist gate.
  • agent/uiVerifier.ts — confirms the UI changed as intended (state verification).
Perception
  • providers/desktop.provider.ts / providers/android.provider.ts — capture the screen and perform input (desktop automation / Android ADB).
  • uiParser.service.ts — turns a raw screen into a compact, LLM-readable UI tree.
  • ocr.service.ts — extracts text from screenshots to enrich perception.
Conversation & memory
  • session.service.ts — persists conversations, history, export (caps via MAX_SESSIONS / MAX_MESSAGES_PER_SESSION).
  • memory.service.ts — a RAG store: past trajectories (goal + actions) and corrections (384-dim Xenova embeddings) in ~/.quenderin/, retrieved by similarity to inform future runs.
  • presets.ts — assistant personas (General/Code/Writer/Tutor/Summary).
  • intentClassifier.ts — routes input between chat and an agent objective.
Tool-use (tools/)

The chat assistant's tool loop:

  • tools/toolLoop.ts — plan → call tool → observe → repeat.
  • tools/registry.ts — the tool catalog (see below).
  • tools/handlers.ts — executes a parsed tool call.
  • tools/calculator.ts — a safe expression evaluator.

Built-in tools: calculator, expression, datetime, system_info, read_file, note_save, note_list.

Voice, daemons, metrics, readiness
  • voice.service.ts — Picovoice wake-word + speech; pipes spoken commands into the agent. Gated on PICOVOICE_ACCESS_KEY (optional).
  • backgroundDaemon.service.ts — passive observation; triggers the LLM only when the screen changes beyond VISUAL_DIFF_THRESHOLD (adaptive backoff when idle).
  • metrics.service.ts — tok/s, TTFT, RAM, loaded-model telemetry.
  • readiness.service.ts — drives /ready and /health.

Utilities (src/utils/)

FilePurpose
logger.tsStructured logging (levels: debug/info/warn/error/critical) — used everywhere instead of console.*
hardware.tsHardware profile (RAM/chip), adaptive timeout multipliers, memory budgets
memory.tsAvailable-memory probing
stripControlTokens.tsCleans model output of control tokens

Conventions

  • No any in shared types without a comment; no @ts-ignore without a comment. Run npm run typecheck after changes.
  • Never hardcode model paths — use the catalog + discovery logic.
  • Never remove safety-blocklist entries.
  • Errors propagate to the UI (via WebSocket error events) — never silently swallowed.
  • New WebSocket message types must be added to the TypeScript interfaces in both directions. See API.md.

Frontend

The dashboard UI in ui/ — React + Vite + Tailwind + TypeScript. In development it runs on Vite (localhost:5173); in production it's built to public/ and served by the Express backend.

Entry & shell

  • ui/src/main.tsx — mounts React.
  • ui/src/App.tsx — the shell: a currentView state switches the main pane, and a first-run WelcomeWizard (gated on localStorage['quenderin_setup_complete']) walks new users through setup.

The Inspector panel overlays the agent view to show live observe/decide/ action state.

State & communication

  • ui/src/hooks/useAgentSocket.ts — the heart of the client. Opens the WebSocket, sends start/chat/settings_update/preset_switch/voice messages, and handles inbound chat_stream/observe/decide/action/done/ error/model_download_progress events, exposing the agent + chat state to components. See API.md for the message catalog.
  • ui/src/context/ThemeContext.tsx — dark/light theme.
  • REST (fetch) is used for non-streaming data: the model catalog, sessions, notes, metrics, voice download.
localStorage keys

Running the UI

bash
cd ui && npm run dev        # http://localhost:5173 (hot reload)

The UI dev server renders the real components, but live data needs the backend running on :3000 (npm run dashboard from the repo root). Without it, the UI shows its offline/disconnected state (e.g. "Loading Model… retrying").

Design rules

The UI follows the project design system: state (:hover, :focus, active) never changes geometry; hairline borders, no card shadows; hierarchy in weight + size; tabular numbers; monospace for codes/metrics. Density beats decoration — this is a developer power tool.

Quenderin Dashboard UI

The React front-end for the Quenderin dashboard — chat, governed tasks, the device agent, metrics, and settings (including the AI Model Manager). Served in production by the local Node backend; run standalone against it during development.

Stack

  • React 18 + TypeScript, built with Vite
  • Tailwind CSS for styling
  • State over a single WebSocket (src/hooks/useAgentSocket.ts) plus REST helpers (src/lib/api.ts — every state-changing call goes through apiFetch, which attaches the per-launch X-Auth-Token)

Development

Start the backend first (from the repo root):

bash
npx tsx src/index.ts dashboard --no-open
# prints: Open this URL to connect: http://localhost:3000/?token=<per-launch token>

Then the UI dev server:

bash
cd ui && npm run dev

Open http://localhost:5173/?token=<token from the backend log>. Vite proxies /api and the WebSocket to localhost:3000 (see vite.config.ts), and the renderer reads the token from ?token= once, then strips it from the URL.

Build

bash
npm run build      # from ui/, or `npm run build:ui` from the repo root

Output lands in ui/dist and is what Electron / the packaged dashboard serves.

Conventions

  • New WebSocket message types must be added to the interfaces on both sides (client src/hooks/useAgentSocket.ts server-message union, server src/types/) and to the tables in docs/API.md.
  • Model management (catalog, download, delete, switch) is REST-only — the WS switch_model twin was removed after it drifted unused (r9 H1).
  • All inference is 100% local (node-llama-cpp); there is no external-provider configuration. (An earlier version of this README described a long-dead Ollama drag-and-drop setup page on port 3777 — that UI no longer exists; r7 C1.)

Quenderin marketing website

A marketing site with static HTML, CSS, vanilla JS, and a self-hosted font. The model tables and calculator data are generated from the shared app manifest. Browsers request only first-party resources; a small Worker reads public Hugging Face metadata for the latest-release feed.

Regenerate the PNG assets

The favicons, apple-touch-icon.png, and og-image.png are generated from the SVGs — edit favicon.svg / og-image.svg, then re-run (requires Google Chrome):

bash
node website/scripts/rasterize.mjs   # → og-image.png, favicon-16/32.png, apple-touch-icon.png

To screenshot the rendered site (full page + every section, light/dark, any width):

bash
python3 website/scripts/serve.py 8099 &                 # static server
node website/scripts/shoot.mjs http://127.0.0.1:8099/ /tmp/shots dark 1440

Preview locally

Any static server works — no build:

bash
cd website
python3 -m http.server 8080
# open http://localhost:8080

Publish the website

The production domain quenderin.org is served by the Cloudflare Worker configured in wrangler.site.jsonc. Static pages use the assets binding; /api/model-releases refreshes public metadata hourly on demand, independently of deployment. The GitHub workflow also maintains GitHub Pages and the Cloudflare Pages preview when its configured secret is present.

bash
npx wrangler deploy --config wrangler.site.jsonc

bash scripts/deploy_website.sh triggers all configured targets, but its GitHub workflow publishes the remote default branch. Push the intended website changes before using that part of the script. A local preview or pushed task branch is not production deployment evidence; check the live launch story and download links.

Current model catalog

Run npm run gen:website-catalog after exporting the shared manifest. Never edit generated table rows or calculator values by hand. npm run check:website-catalog checks the full overview, models page, SEO list and calculator payload. Both CI and deployment enforce catalog parity. See docs/MODEL_CATALOG_FRESHNESS.md.

npm run refresh:model-releases updates the saved offline/static-preview snapshot. The production feed refreshes itself; no credentials, visitor headers or prompts are sent upstream. New metadata never changes installed app recommendations.

Editing

The short homepage is index.html; its “Tell me more” link opens the full overview in tell-me-more.html. Keep English HTML and i18n/en.json in sync, and update all 12 language dictionaries for new copy. Shared styling is in styles.css (CSS variables at the top control the palette); simple-home.css only styles the short homepage.

The design follows the project rule set: hairline borders (no shadows), interactive states change color only (never geometry), hierarchy via weight + size, tabular numbers, monospace for specs.

Content report receiver

A small Google Apps Script V8 web app stores user-approved offensive AI content reports for manual review by Quenderin's developer. The product must show the editable excerpt, optional note, destination, and privacy explanation before an explicit Send report action.

This receiver does not collect a conversation, device identifier, contact address, account, credentials, or model configuration. Text may still contain personal information the user chooses to include. Google hosts the endpoint and storage; its own request handling is separate from this code, which makes no payload or exception log calls.

There are no dependencies to install. The custom code supplies the product's strict schema, receipt reconciliation, and atomic capacity admission around Google's existing Properties and Lock services. No mail, Drive files, Sheets, external requests, advanced services, libraries, schedules, or triggers are used. The manifest explicitly requests no OAuth scopes and disables exception logging.

Request and receipt

POST application/json (optionally ; charset=utf-8) to the deployment's /exec URL. Only these keys are accepted; all except note are required:

KeyType and accepted value
schemaNumber, exactly 1
reportIdLowercase UUID version 4, generated by the client
platformString, exactly android
appVersion1–64 ASCII characters; starts with an alphanumeric character, then alphanumerics or . + _ ( ) - without spaces
sourcelocal-chat, agent, deepseek, remote, or step5
reasonharassment, hate, sexual, violence, dangerous, or other
contentNonblank user-edited excerpt, at most 6,000 UTF-8 bytes
noteOptional string, at most 1,000 UTF-8 bytes; absence becomes ""

Text is preserved exactly; lone UTF-16 surrogates are invalid. Unknown fields and wrong types are rejected. The raw JSON body and the stored canonical JSON envelope must each be at most 8,192 UTF-8 bytes. The envelope includes receipt metadata and JSON escaping; a request within the raw limit can still need a shorter excerpt.

Code-unit guards run before byte counting and JSON parsing. Google receives the HTTP body before this application can check its size.

On verified persistence, including an identical retry:

json
{
  "ok": true,
  "code": "received",
  "reportId": "12345678-1234-4234-8234-123456789abc",
  "receiptId": "87654321-4321-4321-8321-cba987654321",
  "receivedAt": "2026-10-28T00:00:00.000Z"
}

Failure responses contain only {"ok":false,"code":"…"}:

CodeMeaning
invalid_requestInvalid JSON, media type, schema, field, or field byte limit
too_largeRaw request or stored envelope would exceed 8,192 bytes
conflictThe same report ID already has a different canonical payload
unavailableDisabled, full, busy, quota/service failure, corrupt/unknown state, or unverified write
method_not_allowedGET requests; no data or owner interface is exposed

Parse ok and code: Apps Script's TextOutput API does not offer custom HTTP status codes. Google redirects ContentService output to a one-time script.googleusercontent.com URL; the native client must follow that HTTPS redirect to read the JSON response, without reposting the report body there.

HTML, a login page, an unexpected redirect, a timeout, or malformed/missing JSON does not establish delivery. Do not treat HTTP success alone as a receipt.

After an ambiguous attempt, preserve the same ID and exact payload for an explicit manual retry. An identical payload returns its original receipt without another write, even when the inbox is full. Changing any field after a send attempt requires a new UUID; changed content under an existing UUID conflicts.

Missing and empty notes are equivalent, and JSON key order is irrelevant. Do not retry in the background. unavailable can follow a successful write whose readback failed; never claim that such an attempt definitely was not received.

Storage and bounds

One Script Property named report:<reportId> holds one canonical JSON string:

json
{
  "schema": 1,
  "receiptId": "87654321-4321-4321-8321-cba987654321",
  "receivedAt": "2026-10-28T00:00:00.000Z",
  "report": {
    "schema": 1,
    "reportId": "12345678-1234-4234-8234-123456789abc",
    "platform": "android",
    "appVersion": "0.4.1",
    "source": "local-chat",
    "reason": "other",
    "content": "Synthetic fixture excerpt.",
    "note": ""
  }
}

Maximum 32 reports, each at most 8,192 bytes, and at most 262,144 bytes of report values in total. The sole supported configuration property is qr.enabled, exactly the string true or false. Absence means disabled; unrecognized properties or invalid values fail closed.

At most 33 properties are used, within Google's documented 50-property manual management interface. A dedicated standalone script must be used; do not mix this store with other code.

A Script Lock waits at most 200 ms. While held, one full store read validates all records, capacity, and duplicates. A new report uses one property write and one readback. There is no separate counter/index transaction. Existing reports are never overwritten or deleted.

Quota or readback failure returns unavailable without attempting rollback or another write. Lock release runs in finally. An owner changing the enable flag does not cancel an already admitted request.

The endpoint is anonymous and unauthenticated; reports are untrusted allegations, not verified incidents or instructions. Anonymous spam can fill the bounded inbox or exhaust shared Apps Script execution/property quotas. The fixed limits protect storage and prevent automatic downstream work; they do not guarantee availability, remaining account quota, or delivery during an outage. Review cadence and capacity must be checked before this endpoint is offered to users.

Deployment and manual review

  1. Complete independent code review and run the fixture command below. Verify the intended existing consumer Google account and its current applicable terms, included use, quota sharing, and account restrictions. This source does not establish those account facts or authorize paid services. Keep the default Apps Script Google Cloud project; do not attach billing, provision a paid service, enable APIs, or add integrations for this inbox.
  2. In that account, create a dedicated standalone Apps Script project. Paste only Code.gs and enable Show appsscript.json manifest file in editor in Project Settings, then paste appsscript.json. Save. Verify V8, empty scopes, no services/libraries/triggers, and no other code. Do not upload this README or the Node test file into the script project.
  3. In Project Settings → Script Properties, add qr.enabled with the value false. Do not add credentials or other configuration. Keep editor access limited to the report reviewers; anyone with project editor access can read the report store.
  4. Choose Deploy → New deployment → Web app; execute as the deploying owner and grant Anyone access, including people not signed in. The manifest equivalents are USER_DEPLOYING and ANYONE_ANONYMOUS. If anonymous access is unavailable or unexpected authorization scopes appear, stop and resolve that limitation. Use a versioned deployment's /exec URL, not /dev.
  5. Record source revision/hash, deployment ID/version, owner account category, and dated account/quota/permission evidence in the existing release record. Verify public GET returns only method_not_allowed and a bounded synthetic POST while disabled returns unavailable, including JSON after the redirect.
  6. When the reviewed source, owner access, policy/disclosure, Android client, and account limits are verified, deliberately set qr.enabled to true. Send one clearly labeled synthetic report, read its exact stored property in the owner UI, and verify an identical retry returns its original receipt. This uses one of the 32 slots; keep its fixture record identified in release evidence. Do not inject real offensive text or real user information as a test.
  7. The owner reviews reports in Project Settings → Script Properties. Read each report:<UUID> value as JSON, including reason, excerpt, note, version, and timestamp; treat content as untrusted text. There is no public listing, search, download, admin, email, or notification endpoint. Never paste reports into public logs, issue trackers, or test artifacts. Follow the published privacy/retention process for actual reports.

To stop intake, set qr.enabled to false; keep all report properties intact. To recover from full/corrupt storage, keep intake disabled, inspect the exact state privately, and resolve through an explicitly authorized data-handling process. Do not delete reports, reset IDs, raise limits, or replace the project as an automatic recovery step.

There is no automatic purge. Updating/rolling back a deployment must preserve this existing script's report properties and the schema-1 reconciliation behavior.

Verification

Run from the repository root with Node 20+:

sh
node --test services/content-report-receiver/receiver.test.mjs

Fixtures use a fake Script Lock, properties, clock, receipts, ContentService, and logging traps.

They cover normal persistence/readback, canonical retries and conflicts, capacity and overlap, disabled/unknown/corrupt state, byte boundaries and escaping, invalid Unicode/types, quota/lock/write/readback failures, ambiguous-write reconciliation, GET privacy, and the no-scope/no-log/no-network configuration. They install nothing and make no live requests.

Hosted deployment, actual account/terms, owner UI readback, redirects, and native-client behavior remain separate release checks.

Official documentation verified 2026-10-28:

  • Properties Service: script-wide string storage and manual management up to 50 properties.
  • Apps Script quotas: consumer property read/write quota 50,000/day, value limit 9 KB, total store 500 KB; execution limits and quotas are shared and may change, and quota exhaustion stops execution.
  • Lock: bounded tryLock and explicit release.
  • Content Service and TextOutput: JSON output, redirect behavior, and output API.
  • Manifest and web app configuration: V8, exception logging, explicit scopes, deployment identity, and anonymous access.

These are provider documentation checks, not evidence of the current owner's remaining quota or a completed deployment.
