Bonsai 2 27B integration

18 October 2026 engineering candidate

The current candidate extends the pinned Prism runtime rather than treating a catalog row as model support. The normal catalog has 28 entries in matching TypeScript, Swift and Kotlin manifests. The new text paths include the smaller Bonsai 2 models, LFM2.5-24B-A2B, Jais 3, Nemotron 3.5 Bolt, complete Beam and complete Muse on native Apple, Android and desktop. Publisher text protocols have dedicated adapters; tool use is disabled for the experimental Beam/Muse chat paths. Model-weight inference for these additions has not been run. This section describes engineering in the candidate, not a new public installer or store release.

Mobile MAX execution of Bonsai is a separate, blocked milestone: the pinned MAX 26.7 source has no Android backend, no reviewed Bonsai MEF/tokenizer/cache contract exists, and no phone run was performed. See Mobile MAX/Bonsai integration status. No Bonsai result below is a MAX result.

Beam's four-part download is 133,885,310,500 bytes, including its 5,954,020-byte metadata entry point. All four parts are required. Its minimum whole-model memory floor is 160 GiB before context overhead. Muse requires all 22 Q2_K parts, 304,080,474,208 bytes. The desktop adapter now accompanies the native adapters; the older October 16 snapshot below records the earlier scope. Complete hashes, compiled architecture capabilities and actual free-memory checks gate loading. Active parameter counts do not reduce the storage or full-weight memory budget.

The versioned Node addon patch also adds cancellation ABI 1. Atomic context callbacks interrupt CPU evaluation during prefill and decode; GPU cancellation waits for a scheduler graph boundary. Old addons cannot enable specialist or Beam/Muse downloads merely by copying a provenance stamp. A timed-out ordinary model initialization retains its reservation until the actual load finishes; retrying joins that same load. Specialist and image work use an exclusive memory lease, releasing idle text weights before checking available memory. Text model selection and conversation state are retained across that lease.

Still-image questions

Ask about an image installs each complete language-model/projector pair from shared/vision-models.json. It covers MiniCPM-V 4.7 1B and 35B-A3B, and Nemotron 3.5 Super VL 120B-A12B. Their minimum available-memory floors are 8, 32 and 96 GiB. The app accepts one selected JPEG or PNG, at most 8 MiB, 4,096 pixels on either side and 16 million pixels. It preserves the selected file and question after failure or cancellation. Video, audio and tool requests are unavailable.

The app bounds each question to 8,192 UTF-8 bytes, a 4,096-token context and 512 output tokens. The C bridge checks actual token/image context usage before decoding and buffers only the final answer. Its bounded decoder allocator also rejects small compressed PNGs that expand beyond the allocation budget. Both native and desktop workflows install the complete pinned pair, verify both files and recheck available memory before loading. These are still-image question tools, separate from the selected text answer model.

Apple and Android link the C bridge into their existing Prism runtime. Electron uses one static worker in a child process; model paths and prompts travel over bounded stdin. On a hosted target-OS builder, after preparing the pinned source:

sh
python3 scripts/build_vision_runtime.py build --source /absolute/prepared/prism-source --work /absolute/new/vision-build
python3 scripts/test_vision_runtime.py --source /absolute/prepared/prism-source --work /absolute/new/vision-fixtures

The build helper stages the worker, notices and provenance into the existing build/vision/<platform>-<arch> resource directory. Packaging verifies the exact worker, dependency closure, compiled ABI, source patch and artifact manifest. These commands compile code and run synthetic fixtures; they download no weights.

Hy-Memory proposals

The dedicated Hy-Memory proposals workflow uses the pinned 18,236,702,240-byte community conversion in shared/hy-memory-artifacts.json. It is a separate memory writer with a 32 GiB available-memory floor. Paste only the selected conversation, preview proposals, then explicitly select which facts to save. Nothing subscribes to conversations or persists a generated fact automatically.

The official no-thinking HY template, temperature zero and 512-token output cap are fixed. The parser requires one complete object containing only memories, at most 64 strings of 1–512 characters; duplicate fields, reasoning and trailing content are rejected. Approved records use app-private storage and idempotent identities. POSIX permissions and a verified protected Windows DACL are separate platform implementations. The older general Notes bank is not repurposed. Native Apple, Android and desktop workflows keep proposals unchecked until the user approves them. The community converter's expert-width correction from 1,536 to 768 matches the pinned publisher configuration and existing hy_v3 tensor shapes; it is not full-weight inference validation or permission to rewrite an arbitrary imported file.

Granite Switch 4.1 8B

The official checkpoint is ibm-granite/granite-switch-4.1-8b, pinned in shared/granite41-source.json; it is not the older 3B preview. The converter requires the four complete source shards and pinned metadata already on disk. It fetches no weights, installs no dependencies and executes no remote model code. Use the existing environment containing the prepared runtime's converter dependencies:

sh
python3 scripts/convert_granite41.py --runtime-source /absolute/prepared/prism-source --model-dir /absolute/installed/granite --verify-only
python3 scripts/convert_granite41.py --runtime-source /absolute/prepared/prism-source --model-dir /absolute/installed/granite --output /absolute/new/granite-switch-4.1-8b-q8_0.gguf --outtype q8_0

The converter creates a new GGUF plus an adjacent .quenderin.json record and never replaces existing output. Keep both together. The native Apple, Android and desktop Granite chat workflows select and hash that pair, verify actual graniteswitch architecture, 40 weight layers, 4,096 embedding width and a single complete file. They require the pinned converter record and at least 32 GiB of available memory, with a further file-size/context allowance. The receipt is local conversion evidence, not a publisher signature or inference validation. Dedicated text chat uses the publisher's role template without activating decision, guardian or speech modes. The generic unverified family guard remains closed; this explicit receipt-based import is the supported source path for the official 8B checkpoint.

Step 5 Preview on an existing CUDA host

Step 5 uses its official vLLM CUDA backend on the user's own suitably sized Linux GPU host. Quenderin does not provision a server or claim this 600B-class model fits on a phone. shared/step5-backend.json pins the official model and backend revisions, all 26 required weight files (644,100,979,280 bytes) and metadata. With that exact checkout, checkpoint and dependency environment already installed:

sh
python3 scripts/run_step5_backend.py --source /absolute/installed/official-vllm --model /absolute/installed/step5 --verify-only
python3 scripts/run_step5_backend.py --source /absolute/installed/official-vllm --model /absolute/installed/step5 --tensor-parallel-size 4

The launcher verifies source and artifacts, disables model downloads and starts an inner backend plus a loopback gateway. Defaults are ports 18001 and 18000. Use an existing SSH tunnel to the client's literal loopback address, or a secured HTTPS reverse proxy configured for the gateway's loopback Host policy. Never expose the gateway directly on a public interface. The app requires explicit consent for the selected gateway before sending a conversation and checks the pinned readiness contract before each answer. Clients use system TLS validation, no automatic credentials, cookies, redirects or retries, a 180-second deadline, eight exchanges, 32 KiB of history and at most 1,024 output tokens. The gateway admits one GPU request and propagates client disconnection upstream. This app workflow currently supports text chat; it does not send images to Step 5. The native Apple, Android and desktop clients use this same remote-specialist contract. Prompts leave the device for the selected host only after consent.

Image generation and future artifacts

The separate image workflow covers FLUX 3 Image Klein and MOSS Image Base/SFT. shared/image-model-catalog.json pins the complete model, text encoder, VAE and MOSS tokenizer sets. Import the original components through the app; gated FLUX files require the user's own publisher access and license decision. The app does not accept publisher terms or download gated weights on the user's behalf. The native image runtime stays isolated from Prism's GGML symbols and releases its resources before text restoration. Its available-memory floor is 24 GiB. Native clients provide explicit component installation/import. The desktop Images screen and CLI verify a manually prepared component directory, then save a new PNG without overwriting an existing file. The ordinary answer model is not used to expand a short FLUX prompt automatically; supply a complete scene caption.

Nemotron Bolt E4B has no verified public artifact in this candidate. It stays unavailable; no guessed revision, placeholder download or substitute model is presented as that release.

Existing 27B integration

The bonsai2-27b catalog entry is an experimental manual choice. It pins PrismML's PTQ1_0 language weights to a Hugging Face revision and SHA-256, with an exact 5,946,648,928-byte download. The separate vision projector is not integrated. Existing defaults remain unchanged. This does not claim store distribution or measured Quenderin inference performance.

The source/runtime pins are in shared/prism-runtime.json. The custom ternary types and Hadamard activation transforms require the Prism fork; ordinary GGUF support is insufficient. Stock and older binaries reject download and loading. The model has a conservative 7 GB footprint floor plus the usual 30% runtime overhead (9.1 GB estimated working memory). Native fitness also retains its 85% usable-budget gate, so a 9.1 GB app-memory budget is insufficient. Context is capped at 4,096 tokens. Actual allocation still depends on the backend. A compressed file fitting on disk does not prove RAM fit.

Apple

App Store archives use the committed XcodeGen project and shared Quenderin (iOS) and QuenderinMac schemes. Configure Xcode Cloud with the explicit QUENDERIN_RUNTIME=prism environment variable and Archive actions for App Store distribution. The post-clone hook builds the pinned iOS device and universal Mac framework before package resolution. Later hooks validate the checkout through CI_PRIMARY_REPOSITORY_PATH and reject missing release inputs.

The release profile forbids stock or mock fallback. The final Cloud hook verifies the App Store signed export at CI_APP_STORE_SIGNED_APP_PATH (one iOS IPA, macOS PKG, or app), because Cloud's intermediate archive may use ad-hoc signing. It checks the embedded runtime, model catalog, version/build, team signature and native ternary capability on Mac. Package extraction rejects unsafe paths, ambiguity and oversized payloads, uses fresh scratch, and never runs an installer. The separate verify-archive command still requires a signed archive. Mach-O section identity survives Xcode signing and thinning; source framework files also have complete SHA-256 digests. Runtime deployment minima are iOS 16.4 and macOS 13.3. The 0.4.0 candidate uses build 16; refresh Cloud's counter before starting it.

On 12 October 2026, Xcode Cloud build 15 from 9bab8d8aa67f2ecfdeb93b7a88cc4aed59592568 passed both App Store archive actions and signed-export verification. On 16 October, both iOS and macOS 0.3.0 (15) were verified Ready for Distribution. This does not establish distribution of the new 0.4.0 candidate. See RELEASE.md for live console identifiers, recovered signing procedure and the new release's remaining gates.

sh

Windows and Linux desktop

The pinned node-llama-cpp 3.19.1 addon requires the versioned C API patch in scripts/patches/node-llama-cpp-3.19.1-prism-e8fd209.json. It maps model loading options to Prism's load-mode enum, adapts the repetition and DRY samplers, and allows the packaged loader to locate a verified build without a source checkout. The patch checks complete official source hashes before changing any file, and retains the originals. Do this in a fresh dependency installation after checking disk headroom. Git, Python 3, Node.js 20+, CMake and the platform C++ toolchain must already be available (MSVC Build Tools on Windows).

sh
python3 scripts/prepare_prism_node_runtime.py prepare --package-dir node_modules/node-llama-cpp
node node_modules/node-llama-cpp/dist/cli/cli.js source build --gpu false --ciMode --noUsageExample
python3 scripts/prepare_prism_node_runtime.py verify --package-dir node_modules/node-llama-cpp

The current desktop loader selects this deterministic CPU build. After building, run node scripts/verify_prism_node_runtime.mjs. This loads the compiled addon with builds, downloads and prebuilt fallback disabled; it verifies exact runtime metadata and executes the native PQ2_0/PTQ1_0 block-size and packed-size exports. It establishes native binding capability, not full-model generation quality.

On Windows, use the installed Python launcher (py -3) in place of python3. The helper fetches the exact pinned runtime into the package's new llama/llama.cpp checkout, then writes the official Node source metadata from the verified repository/revision. It refuses an existing source checkout, or backup directory; use a new build workspace if either exists. The official 3.19.1 package's stock llama.cpp.info.json is accepted only at its exact published SHA-256 preimage, preserved in the backup, and patched to the verified Prism pin. Changed, custom or symlinked metadata is rejected before fetching or changing any file. A repeated successful preparation verifies the same files without overwriting them. Do not use source download: that upstream command removes an existing checkout. A direct-I/O and memory-lock combination with mmap disabled is rejected explicitly because Prism has no equivalent load mode.

Desktop packaging keeps llama/localBuilds/** (including its native addon and build metadata), llama/lastBuild.json, llama/llama.cpp.info.json, and llama/quenderin-prism-node-runtime.json. The source checkout and original-file backup are build inputs and are excluded from release packages. The loader's packaged path requires the exact preparation stamp and source metadata; it does not alter standard, unstamped installations or authorize runtime compilation.

Quenderin probes an already-built local addon without downloading/building a backend, and checks its reported repository and exact revision again before loading. Catalog requests never compile a backend. A missing compatible addon leaves Bonsai blocked with a runtime message. Electron release packaging must carry that custom addon; a stock prebuilt does not establish support.

Local image runtime

This is an experimental source integration of FLUX 3 Image Klein and MOSS Image Base/SFT. No model weights or generated-image inference were used to verify it. The immutable component manifests are shared/image-model-catalog.json; the upstream source and patched GGML pins are shared/diffusion-runtime.json.

Build this directory in a separate CMake configure from llama.cpp. The image runtime uses patched GGML, including GGML_MAX_NAME=160 and INT8-convrot support. Reusing llama's ggml CMake target or merging both static archives is unsafe. The final dynamic framework/ELF library exports only quenderin_diffusion_*. scripts/prepare_diffusion_runtime.py verify-library must pass for each slice. The Apple build also renames GGML's Objective-C helper class to QuenderinDiffusionMetalClass; hidden exports alone cannot isolate ObjC classes.

On hosted builders:

sh
python3 scripts/prepare_diffusion_runtime.py fetch --destination "$RUNNER_TEMP/quenderin-diffusion-source"
cmake -S native/diffusion -B "$RUNNER_TEMP/quenderin-diffusion-build" \
  -DDIFFUSION_SOURCE_DIR="$RUNNER_TEMP/quenderin-diffusion-source" -DCMAKE_BUILD_TYPE=Release
cmake --build "$RUNNER_TEMP/quenderin-diffusion-build" --target quenderin_diffusion -j 2

For Android use the project's NDK toolchain, arm64-v8a and API 28 or higher; the final DSO sets 16 KB ELF segment alignment. Keep its own GGML/backends private and use c++_static inside each isolated DSO. Only C/JNI types cross their boundary; hidden C++ symbols and contained exception/allocation ownership avoid an additional shared-STL dependency. The final package verifier checks ELF dependency closure and 16 KB segment alignment, as well as the exact image bytes. For Apple, cross-build the dynamic framework for the actual iOS/macOS SDKs with Metal embedded, set the existing deployment minima, then assemble an XCFramework. No simulator is needed to compile the device and macOS slices. Sign/embed the framework through the existing Xcode Cloud application workflow.

Windows desktop uses the same private patched-GGML DLL and CLI. In a hosted Visual Studio 2022 x64 developer environment, after the source fetch above:

powershell
cmake -S native/diffusion -B "$env:RUNNER_TEMP/diffusion-build" -A x64 `
  -DDIFFUSION_SOURCE_DIR="$env:RUNNER_TEMP/quenderin-diffusion-source"
cmake --build "$env:RUNNER_TEMP/diffusion-build" --config Release `
  --target quenderin_diffusion quenderin-diffusion-cli --parallel 2
python scripts/prepare_diffusion_runtime.py verify-library `
  --library "$env:RUNNER_TEMP/diffusion-build/bin/quenderin_diffusion.dll" --platform windows
& "$env:RUNNER_TEMP/diffusion-build/bin/quenderin-diffusion-cli.exe" --version

Release/debug output paths are stable: bin/quenderin_diffusion.dll, bin/quenderin-diffusion-cli.exe, and lib/quenderin_diffusion.lib (import library, not a second inference runtime). Package the DLL beside the executable and use the project's existing MSVC runtime distribution. The .def file lists the seven shim exports; automatic Windows symbol export is disabled. Inspection uses dumpbin /EXPORTS or llvm-readobj --coff-exports, and fails closed if neither inspector exists or any unexpected symbol is exported.

Windows API paths and CLI arguments support UTF-8/UTF-16 conversion. Only local drive paths are accepted: UNC, device namespaces, alternate data streams, DOS device aliases, reparse points and trailing-dot/space aliases are refused. Model handles and their ancestors remain pinned while the upstream path-based loader runs. Output creation holds parent handles, uses CreateFileW(CREATE_NEW), and checks the resulting handle's final path before writing pixels. Writes are bounded and flushed; failure cleanup marks only the same newly created file handle for deletion. A failed close/cleanup can retain that new output, and never authorizes deleting a path that may now name another file.

Small hosted Windows filesystem checks do not need upstream source or weights:

powershell
cmake -S native/diffusion/tests -B "$env:RUNNER_TEMP/diffusion-fixtures" -A x64
cmake --build "$env:RUNNER_TEMP/diffusion-fixtures" --config Release --parallel 2
ctest --test-dir "$env:RUNNER_TEMP/diffusion-fixtures" -C Release --output-on-failure
python scripts/prepare_diffusion_runtime.py verify-library `
  --library "$env:RUNNER_TEMP/diffusion-fixtures/bin/quenderin_diffusion.dll" --platform windows

These synthetic checks cover Unicode PNG output, existing/racing originals, Windows aliases, pinned parents and reparse rejection. Reparse tests are marked skipped (exit 77) when Windows symlink privileges are unavailable; a skip is a verification gap. The fixtures do not fault-inject WriteFile/flush failures or establish actual Windows model inference.

Swift imports QuenderinDiffusion; JNI should call the same small C ABI from its own adapter. No upstream/GGML structures cross that boundary. Call generation on a worker actor/executor. A single process-wide image job is admitted; concurrent requests return BUSY. Cancellation uses the real upstream cancellation API. The upstream synchronous model loader cannot be interrupted: cancellation during loading is remembered and stops before sampling once loading returns.

Components must already exist at canonical absolute local paths. The runtime does no networking or installation. Run verify-components after installation and before exposing a model as ready. Keep request strings/reference pixels and the engine handle alive until the synchronous call returns. Destroy only after generation returns. Native callers marshal progress to their UI thread.

The output is one PNG at a caller-provided new path. Existing files and symlinks are refused. Dimensions are multiples of 16 from 64 through 1024; steps 1–50, threads 1–8, references at most 10. MOSS accepts text only. FLUX takes full scene captions: expand prompts and reference-image edits with a local LLM before calling this ABI. The source integration does not include that LLM. Package bytes are disk requirements, not measured peak RAM; mobile availability needs a conservative hardware gate and later real inference evidence.

The runtime is MIT and MOSS weights are Apache-2.0. FLUX weights are publisher gated under FLUX Kommunity License v1.0.
